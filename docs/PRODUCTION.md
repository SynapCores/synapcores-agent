# Running this agent in production

The agent code never changes between a laptop demo and production — **only the
gateway's model configuration does.** SynapCores is the brain, and which LLM +
embedding model the brain uses is an operator choice you make in the gateway's
`gateway.toml` (`[query.ai_service]`), not in the agent.

This is deliberate: we don't turn-key a single model on you. The bundled model
gets you running with **zero API keys**; for production you point the same
gateway at a production-grade model and **restart — no agent change, no re-code.**

> The agent auto-adapts to whatever embedding model you choose: at startup it
> probes `vector_dims(EMBED(...))` and sizes its vector columns to match (384 for
> the bundled MiniLM, 1536 for OpenAI, etc.). See *Embedding dimension* below.

---

## The model is a gateway config, not agent code

All of the agent's intelligence is `EMBED` / `COSINE_SIMILARITY` / `GENERATE`
executed by the gateway. The gateway resolves those to a provider via one block:

```toml
# /etc/synapcores/gateway.toml
[query.ai_service]
provider = "native"     # native | openai | anthropic | gemini | ollama
model    = "..."        # the completion/generation model
# api_key / base_url / embedding_model depending on provider (below)
```

Change `provider`, restart the gateway, and every `GENERATE` the agent issues now
runs on the new model. The Python you forked stays byte-for-byte identical.

---

## Option A — bundled model (default, zero keys)

What you get out of the box. No configuration required.

```toml
[query.ai_service]
provider        = "native"
model           = "llama-3.2-1b"            # bundled GGUF completion model
embedding_model = "all-MiniLM-L6-v2"        # bundled embeddings (384-dim)
```

- **Pros:** free, fully local/offline, no API key, no data leaves the box.
- **Cons:** the small (~1B) bundled model produces serviceable but sometimes
  rambly prose. Great for trying the agent + proving the loop; for customer-facing
  replies, use Option B or C.
- **Cold-start note:** the first `GENERATE` lazily loads the GGUF (~30 s on CPU),
  which can exceed the default 30 s `request_timeout`. Raise it once:
  ```toml
  [server]
  request_timeout = 300
  [query]
  default_timeout_ms = 300000
  ```
  After warm-up `GENERATE` is sub-second. (A future release warms the model on
  boot so this isn't needed.)

---

## Option B — cloud LLM for top-quality replies (OpenAI / Anthropic / Gemini)

For the most polished prose, generate the **replies** with a cloud model while
SynapCores stays the **memory + retrieval brain**. Embeddings and chat are
configured independently (cloud providers use different models for each):

- **Embeddings (the vector cognition) stay in the engine.** Keep the bundled
  zero-key MiniLM (Option A), or point the gateway at a cloud *embedding* model:

  ```toml
  [query.ai_service]
  provider = "openai"
  model    = "text-embedding-ada-002"   # 1536-dim, used for EMBED()/COSINE_SIMILARITY
  ```

  Key via the environment (read directly, never in the config file):
  `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `GEMINI_API_KEY` (or `GOOGLE_API_KEY`).

- **Replies are generated by your cloud chat model** (e.g. `gpt-4o`,
  `claude-3-5-sonnet`). [`examples/record_session.py`](../examples/record_session.py)
  shows this exact pairing — SynapCores embeddings + memory/RAG/routing, OpenAI
  `gpt-4o` for the reply — and is the template for wiring a cloud generator.

> **Re-seed when you change the embedding model.** Vectors of different
> dimensions aren't comparable. The agent auto-sizes its columns to the live
> model (it probes `vector_dims(EMBED())`), but existing rows must be re-embedded:
> ```bash
> python -m synapcores_agent --reset && python -m synapcores_agent --seed
> ```
> The same applies to any recipe that hardcodes `VECTOR(384)`.

For a single in-engine setup that does both embeddings **and** replies with no
API key and no app-layer wiring, use Option A (bundled) or Option C (Ollama).

---

## Option C — bigger local model (Ollama, no API cost)

The middle path: a larger model running locally, no per-token cost, data stays
on your infra. Run [Ollama](https://ollama.com) alongside the gateway.

```toml
[query.ai_service]
provider = "ollama"
model    = "llama3.1:8b"                       # any model you've `ollama pull`ed
base_url = "http://host.docker.internal:11434" # your Ollama endpoint
```

```bash
ollama pull llama3.1:8b
```

Good when you want better answers than the bundled 1B but can't send data to a
cloud API. (For best results pull a dedicated embedding model too and re-seed, as
in Option B — Ollama embeds with the configured model.)

---

## Option D — swap the bundled GGUF (advanced)

Keep everything local but run a different/larger GGUF than the shipped default:
set `provider = "native"` with your model name and make the GGUF available to the
container's model directory (mount it in), then restart. Most operators find
Option C (Ollama) simpler for running a bigger local model; reach for D only when
you specifically want the in-process native runtime.

---

## Embedding dimension (why the agent "just works" across models)

`brain.py` no longer hardcodes 384. On `ensure_schema()` it runs:

```sql
SELECT vector_dims(EMBED('probe'));
```

and sizes `VECTOR(N)` to the result — so the identical agent runs on MiniLM (384),
OpenAI (1536), or any other embedding model, with the only operator action being a
**re-seed when you change the embedding model**.

## Quick decision guide

| You want… | Use | Notes |
|---|---|---|
| Try it now, no keys, all in-engine | **A — bundled** | rambly prose; raise `request_timeout` |
| Better quality, no cloud / no cost, in-engine | **C — Ollama** | run a local 7B–8B; simplest upgrade |
| Best prose (cloud LLM for replies) | **B — cloud LLM** | embeddings in-engine + LLM at the app layer; see the demo; re-seed after embedding switch |
| Local in-process, custom GGUF | **D — native swap** | advanced; usually prefer C |
